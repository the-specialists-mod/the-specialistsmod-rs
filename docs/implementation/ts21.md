# The TS 2.1 gameplay plugin

`ts_gameplay 21` makes the server play by TS 2.1's rules, the April 2004 `mp.dll` and
`client.dll`. The decomp's reports are in `docs/ts21/` and posted on issue #100. The plugin is
the crate `crates/ts21` (package `ts21-gameplay`). It plugs into the hooks described in
[gameplay-plugins.md](gameplay-plugins.md), and the 3.0 crates never name it.

## Status

The plugin is registered on both sides and selectable end to end: the cvar (latched at a map
start; a change reloads the map, [gameplay-plugins.md](gameplay-plugins.md) §4),
physinfo `gp` and `SrvSett` 4 all work (issue #100 checklist item 1). TS 3.0's own client is
refused in 2.1 mode (§4.2 there); only the port's client, bots and HLTV join.

Done:

  cap ([Movement](#movement)).
* **Item 3, shared weapons:** the 2.1 tables, fire timing, spread, pellets and prediction
  ([Shared weapons](#shared-weapons-issue-100-23-checklist-item-3)).
* **Items 8, 9:** power-ups, slow motion and the server stunts
  ([Power-ups and slow motion](#power-ups-and-slow-motion-issue-100-37), [Stunts](#stunts-issue-100-38-slot-limits-35)).
* **Items 10, 14:** the map entities and the protocol translation

**In-engine** (issue #103): `cargo xtask ts21` ([validation.md](../validation.md) §2.y) runs 2.1

Every other hook keeps TS 3.0's body. The remaining items of the issue's checklist add the 2.1
rules here, each with any hook it needs (added to the 3.0 crates with the 3.0 behaviour as the
default).

## Layout

| Package (directory) | Implements | Linked by |
|---|---|---|
| `ts21-gameplay` (`crates/ts21`, `src/shared/`) | `shared::gameplay::PmRules` and `GunRules` on `Ts21`: movement and the gun, which the server and the client's prediction both run (issue §2). The id `"21"` | both libraries |
| `ts21-server` (`crates/ts21/server`) | `ts_server::gameplay::ServerRules` on `Ts21Server` (issue §3), and the server's `PLUGIN` | `server-dll` |
| `ts21-client` (`crates/ts21/client`) | `ts_client::gameplay::ClientRules` on `Ts21Client`: HUD and input (issue §4), and the client's `PLUGIN` | `client-dll` |

The side hooks are packages of their own, not cargo features, so a build of both libraries never
links the server crate into the client library or the other way round
([gameplay-plugins.md](gameplay-plugins.md) §1). `server-dll` registers `ts21_server::PLUGIN`
under the id `"21"` at `GameDLLInit`, and `client-dll` registers `ts21_client::PLUGIN` at
`Initialize`. Both do it behind their default-on `ts21` feature, after TS 3.0's (`ts30`), so
either ruleset builds alone ([gameplay-plugins.md](gameplay-plugins.md) §8).

## Rules

* Match TS 2.1 exactly, including its oddities, as the port matches 3.0 (AGENTS.md). Cite the
  2.1 function and address (`mp.dll`/`client.dll` VAs, `0x1000xxxx`) in doc comments.
* The wire format stays 3.0's (issue #100 §1.2). The plugin carries 2.1 values in 3.0's messages.
* Never copy behaviour that crashes, hangs or stops the engine. Guard it and list it below.

(issue #100 §1.2), and the server's stunt code converts. The time scale also keeps the port's
encoding, where 1.0 is normal (2.1 uses 0), so the 2.1 guards for 0 only matter before a
player's first spawn.

### Arithmetic

* 2.1 `mp.dll` runs the x87 at 53 bits, as 3.0's does (its CRT sets `_PC_53` at 0x1006fa8b), so
  `Arith::Msvc` reproduces its finite arithmetic. The overrides reproduce its stores and
  operation order, written generically over `shared::pm::Fpu`.
* 2.1's compiler tests `fcom` through the parity flag, so its comparisons follow IEEE for a NaN
  (Rust's operators). Every float compare in its SDK pm code (0x1002f540-0x100342e0) and its TS
  pm block (0x10057d10-0x10058fd0) does; the only `test ah,0x40` there are integer `flags`
  tests. The overrides use IEEE compares, and the SDK movement both rulesets share follows them
  through `ieee_compares` (issue #105): under `Arith::Msvc` the movement runs `shared::pm`'s
  `MsvcIeee` build, the same arithmetic with each compare as the C operator's IEEE result
  (`Fpu::cmp_eq`/`cmp_lt`/`cmp_le`). So a NaN `waterjumptime` water-jumps and blocks
  `PM_Accelerate`, a NaN `flSwimTime` doesn't wade, a NaN length normalises, a NaN pitch doesn't
  stop `PseudoClimb` (0x10057d84), and so on, as in 2.1. Under `ts_pm_arith gcc` the compares
  stay `ts_i386.so`'s.
* 2.1's `client.dll` is an unoptimised build that stores every intermediate to a `float`
  (`PM_Accelerate` cl21 0x1005aef0, `FixVelocity` cl21 0x100919b0), so 2.1's own prediction
  could differ from its server in the last bit. The port predicts with the server's arithmetic
  instead, so client and server agree exactly (see Deviations).
* TS 2.1 shipped no Linux server. With the server's `ts_pm_arith gcc`, the overrides run 2.1's
  formulas with `ts_i386.so`'s rounding (every value the C stores rounded to a `float`). There is
  no 2.1 GCC build to compare against.

## Rules, scoring, cash, cvars and commands (issue #100 items 6, 7, 11)

`ts21-server` (`crates/ts21/server/src/`): `rules.rs`, `scoring.rs`, `cash.rs`, `players.rs`,
`cvars.rs`, `commands.rs`. Addresses are 2.1 `mp.dll` VAs; decomp `docs/ts21/rules.md`.

### Game modes and teams (`rules.rs`)

* **The mode comes from the map name** (`DecideGamePlay` 0x100433b0, case-sensitive prefix):
  `tm_` objective rounds (3), `tr_`/`cs_`/`de_` round team deathmatch (2), `ts_` teamplay in The
  One mode, else `mp_teamplay`. There is no worldspawn `gamemode` key. `mp_theonemode` is read at
  map load; on a map that isn't `ts_` The One still runs, on DM rules.
* **LMS is the live `lastmanstanding` cvar** in DM (Think reads it every frame), not a mode.
* **Round modes 2/3** (`InstallGameRules`, `CTSGameRules::Init` 0x10044810): teams "Specialists"
  (model `seal`) and "Mercenary" (`merc`), each with team cash `(int)initial_cash`; the first
  round starts 5 s in. `InitObjectives` makes it mode 3 when the map has a
  `ts_objective_manager` (at every round restart; at install no entity exists yet, so the first
  5 s are mode 2, as in 2.1). Specialists spawn at `info_player_start`, Mercenaries at
  `info_player_deathmatch`, and in mode 2 the sides swap every third round.
* **Rounds:** Think's round branch, `TeamWin(team, win, lose)` (0x10044d00: team cash
  `min(max(c + win, initial), 30000)` for the winner, `max(c + lose, initial)` otherwise; with
  under two players the team cash and scores start again and "Waiting other players."),
  `RestartRound` (0x100445d0: no refund, players pick up their team cash, join deadline 25 s,
  respawn in 3 s), `ResetRestartRound` (0x10044ba0, restart in 3 s; `n >= 2` also clears the team
  cash and scores), `CheckDeads` (0x10045940: LMS counts a pending respawn as standing; mode 2
  team wins and draws). `TSHVoice` and the "Specialists"/"Mercenary" `TeamScore`s.
* **Objective rounds (mode 3, issue #66).** `InitObjectives` (0x100449b0) keeps up to 32
  `ts_objective_manager`s and, in mode 3, disables every `ts_bomb`, `ts_hack` and `ts_teamescape`
  and starts every `ts_wingiver` counting again (`rules::disable_objectives`); `SetObjective`
  (0x10045150) clears the objective list and runs a random manager's `Reset` (its `messagea..d`,
  then `objptargeta..h`, which usually fire `ts_objective_ptr`s). The round's end calls
  `RoundTimeLeft` (0x100450f0): the manager's `targetontimeleft` while the round has an end time
  (every frame until a `TeamWin`), else a draw; the bomb's explosion calls it too. `CheckDeads`
  fires the manager's `targetonspecdead` when only Mercenaries stand, `targetonmercdead` when only
  Specialists do, and draws when nobody does. A `ts_wingiver` (`Use` 0x10050d10) calls 2.1's
  `TeamWin(team, win, lose)` with `cashforwin`/`cashforlose`, or its own `victorycash`/`defeatcash`
  while the cvar is 0 (`ServerRules::giver_team_win`). The respawns per round are the first
  `ts_mapglobals`' `playerrespawn` (Think copies it once, `entities::map_globals_keys`).
* **The objective entities** are 3.0's (`ts_server::entities::ts::objective`) with 2.1's rules
  (`rules::OBJECTIVES`, `ServerRules::objectives`): their HUD lines use effect 1 (top), as do
  `ts_slowmotion`'s message and the `ts_dmhill` award (issue #221); `attackerteam`
  0/1 means the player's team is "Specialists"/"Mercenary" by name (no -1 for anyone), the escape
  zone counts that team by name, and a pointer's text is `objmsgspec` for a Specialist and
  `objmsgmerc` for anyone else; the pointer enables only bombs, hacks and escape zones; the list
  appends on every use (no search), only a freeze sends `DelObj` (`ShowObj(idx, 0)`; an objective
  not in the list zeroes its count) and nothing resends it; `PreThink` runs 3.0's `CheckForWires`
  (FUN_10055650) twice a second in the objective mode, as 3.0 does (issue #241); a timer runs out at `t <= 0` (a NaN keeps
  running, and its wires can still be cut); `SetObjective` leaves the list alone outside the round
  modes. `cutwire_<n>` is 3.0's (FUN_10055700 is the same).
* **Teamplay on DM maps** is the SDK's model teams: the team list is `mp_teamlist` (no 4-team
  table, no `mapteams`/`teammodels`/`mp_teammodels`), `SetDefaultPlayerTeam` reads the `model`
  key, and each team's model is its name. In The One mode the players' models and teams are
  `mp_theone` and `mp_theothers` (16 bytes of the cvar, `strncpy` 0x1003895b..0x1003897e).
* **Team changes** (`ServerRules::team_changes`, #238): `ChangePlayerTeam` (0x10038cb0) takes the
  name it is given and only an empty one goes to the smallest team: no `IsValidTeam` test and no
  The One override, so `jointeam N` in The One mode joins the team asked for until the next
  spawn's `SetDefaultPlayerTeam`. `ClientUserInfoChanged` (0x10038f50) has no team-limit case: in
  TDM a `model` key naming a listed team changes team the SDK way (announced, logged, observer and
  a forced 5 s respawn), an unlisted one gets "Can't change team" / "Server limits teams to"; in
  The One mode a changed `model` runs `SetDefaultPlayerTeam` again.
* **Spawn spots** (`FUN_10043010`, `ServerRules::spawn_spot_master_test`, #239): every spot of the
  class is scored; there is no `IsTriggered` (`master`) test.
* **The One:** `SetPlayerTheOne` (0x100467c0) without the speed change or log line;
  `SelectRandomTheOne` (0x100466e0) doesn't look for a One first, and Think calls it every frame
  while there is none, plus the 10 s check, which looks at slots 0..maxClients-1 only (0x1004439c), so while The One is in the last slot another One is picked every 10 s; after a kill The One gains 10 health per player up to
  200 (teamplay `PlayerKilled` 0x100392e0, counting slots 0..maxClients-1 as compiled); overheal
  decays to 100 for everyone, The One included, and nothing regenerates. `TheOneIsDead`
  (0x10046930, `players::the_one_is_dead`, #250) calls `SetDefaultPlayerTeam` on the dead One,
  `SetPlayerTheOne` on its killer and `SetDefaultPlayerTeam` on the killer: no `ChangePlayerTeam`,
  so the new One stays in play with its cash; with no killer "The One is dead" (no full stop).

### Scoring (`scoring.rs`)

`TSGetPointsForFrag` (0x1004f3c0) and `PlayerKilled` (0x1004f7e0): a stunt kill +2 with no speed
test, a slide +1, both stacking on close combat (kung fu + stunt = 4); round modes score plain
points; English frag messages (`"%i frags for %s, %s"`, " style!", "Kung-Fu"); double kill
within 1 s, the last-kill time always updated; sprees +30 / +50 / health set to 150 with kung fu,
super jump and a 3 s slow pause; killing The Specialist +5 and a 3 s slow pause; no specialist
suicide penalty; no headshot/knife/katana/coldcock lines; death-cam slow point 0.15 for 1.5 s;
`slowmatch` caps the held slow motion at 5 s. A suicide or a death by a non-player takes the frag
from the **attacker's** pev (0x1004f87f): a world kill costs the world a frag and the victim
keeps its frags. Kill logs carry no 3.0 tags. The kill's weapon name (DeathNotice `FUN_1004ede0`) is 3.0's but for two spellings (`scoring::WeaponNaming`): a thrown blade is its classname, so every blade is "Throwing Knife", and a stock hit is just "Stock".

**Plugin API version 5** (port addition, #198; [plugin-api.md](plugin-api.md) §1.3): 2.1's
`PlayerKilled` reports every death it scores to the plugins' `kill_scored`, as 3.0's does,
through the shared `ts_server::rules::scoring::kill_report` / `report_kill` (killer, victim,
inflictor, the blow's weapon id and the `DeathMsg` name, 2.1's spelling) with 2.1's own values:
`points` as 2.1 scored them (the style points, the double kill, The Specialist's +5 and
Unstoppable's doubling; the plain point in the round modes; 0 for a non-One killer in The One
mode, a suicide or a death by no player),
`killer_spree` the spree 2.1 kept (it only grows in DM/TDM on a scoring kill), `victim_spree`
before the death, and the tags 2.1 has (`scoring::kill_flags`): `stopped_fury` /
`killed_specialist` / `double_kill` / the spree award (Killer 3, Demolition Man 6, The
Specialist 9, Unstoppable 10 on) from the DM/TDM spree part when it ran, `diving` / `sliding`
from `TSGetPointsForFrag`'s "Stuntman" / "Sliding" styles, the kung-fu frag ("Kung-Fu" by the
killer's own hand), `killed_the_one`, and the damage globals. Never set in 2.1 mode:
`victims_weapon` (2.1 has no such test) and `HEADSHOT` (2.1 keeps no `glast_headshot`, `damage.rs`).

The other version-5 callbacks: 2.1's kung fu (`ts21_gameplay::shared::melee::ccombat_attack`,
`CCombatAttack` 0x1004de10) asks `melee_attack` through the same `GunHost::melee_attack_pre` as
3.0's, once the move is picked, with the move's delay before 2.1's time-scale factor `T` (which
then applies to the answer as to the move's own: the next attack in `T × time`, `BlockPlayer`
0.9 of it) and the damage a hit deals (2.1's bar scaling and the Kung Fu doubling applied). A
blocked move holds nothing (the sweep's and flying kick's crouch), spends no bar and plays
nothing; its delay still runs. The stock hit, the blades and the stunt kicks don't ask, as in
3.0. `player_stunt` and `player_powerup` need nothing of 2.1's own: its stunts are the core's
moves (`ts_server::stunt::moves`, with 2.1's `StuntRules`) and its power-ups the core's
`use_powerup` / `add_powerup` (with 2.1's `PowerupRules`), which call them. 2.1 has no wall
dive, so a stunt-key press at a wall is a wall jump or a plain dive.

### Cash and buying (`cash.rs`, `players.rs`)

* `CashBased()` (0x100435f0): the round modes, or Think's `(int)usecash` copy non-zero.
* Join: `InitHUD` sets the cash to `(int)initial_cash` (no `ClientPutInServer` cash). 2.1's
  `CTSGameRules::InitHUD` (`FUN_100451c0`) is the last call of `CHalfLifeMultiplay::InitHUD`
  (0x10023ec0), so in teamplay it runs before the teamplay part's `ChangePlayerTeam`, whose forced
  5 s respawn (a mid-round joiner of round TDM sits the round out) and cash floor stand
  (`InitHudRules::inside_multiplay`, #231). It sends no `Spectator` list, its notices are "This
  server have cheats enabled." / "This server have custom weapon damages (%.2f)" with effect 1,
  and `SrvSett` 0 is the live `realbullet != 0`. The floor
  `FUN_10042c90` (team cash in the round modes, then `initial_cash`) runs at `StartObserver`,
  `Killed` and `TSInit`.
* Kill cash: points × 900, only in DM/TDM while cash-based.
* `BuyArmament`, `BuyWeapon`, `AddItem`, `BuyAmmo` (0x100559d0, 0x10055e00, 0x10055c30,
  0x10055a40): the weapon's cost and the attachments (silencer 900, laser 800, flashlight 500,
  scope 1800) are charged when cash-based and refused below 0; M61s only in the round modes, two a
  round (the count, `+0x68c`, is zeroed only by `RestartRound` and `InitHUD`, #247); kevlar (1900) and stealth shoes (700) only in the round modes; kevlar sets the armour to
  100 and weighs nothing.
* `PickUpWeapon` (0x10055830) charges `free_slots − slots` with no akimbo refusal and no stack
  multiplier (`ServerRules::pick_up_cost`): a hand-typed `tkw` with the akimbo id of a single gun
  (10, 16, 30) buys the pair, built by `GiveWeapon` from the single's record, without the single.
* `Killed` in DM/TDM drops an armour power-up holding the remaining armour.
* A corpse's M61s: `DropWeapon` (FUN_10056080) has no dead-player branch, so `Killed` throws one
  M61 world gun with the drop sound, in every mode; 3.0 turns them into grenade power-ups
  (`ServerRules::dead_grenades_become_powerups`).
* A knife stack: `DropWeapon`'s stack branch throws one knife per drop (`clip = 1`), disarm or
  not, so a corpse leaves one knife and keeps the rest; 3.0 throws the whole stack except on a
  disarm (`ServerRules::stack_drop_count`, issue #166).
* Respawns (`SetPlayerRespawnTime` 0x10042d50): mode 3 by `ts_mapglobals` `playerrespawn`, mode 2
  and LMS by `respawnnumber`, join deadline 25 s. Both count lives: `Killed` adds the death
  (`+0x732`) before the call, so `respawnnumber 1` (the default) leaves a player killed in a

## Stunts (issue #100 §3.8, slot limits §3.5)

`crates/ts21/server/src/stunt.rs`. Decomp `docs/ts21/movement.md` §3, checked against the 2.1
code.

* **Absolute timers** (`ServerRules::stunt_clock`, `Absolute`): every stunt timer is an end time
  `gpGlobals->time + d * slowInv`, fixed when it starts, with `slowInv = 1 / max(fuser1, 0.1f)`
  (`FixedSlowMul` 0x1005a3d0, `FixedSlowAmt` 0x1005a3b0). Nothing counts them down; they run
  while `t > time` and are over once `t < time` (`Play` 0x1005acf0, `BlockPlayer`'s lock in
  `PreThink` 0x100537e0). `NextStunt` sends `trunc((next - time) * 10)`. The coyote window is
  `0.7 * slowInv`, and the weapon delays a stunt sets are `d * slowInv`. The kung-fu and katana
  timers the gun writes (`recover`, the kick cooldown, `BlockPlayer`) go through the same clock.
* **Slot limits** (`can_dive`): used slots below 22 / 42 / 72, nothing bypasses them. In the
  round modes (mode 2/3) a high stunt also needs `armorvalue <= 0` (`CanDiveHigh` 0x1005b0b0:
  `fcomp 0.0; test ah,0x41; jp` refuses above 0 or on a NaN). The decomp report and issue
  #100 §3.5 read this as "needs armour"; the code says the opposite.
* **Recoveries** (`StuntRules`): dive roll-out 0.75 (`Landing` 0x1005c4e0), flip 0.5
  (`HandleWheel` 0x1005c040), get-up 1.0 (`HandleSlide` 0x1005c1f0), wall jump/climb landing 0.5
  and it sets `RECOVER` (`HandleWallJump` 0x1005bd80, `HandleWallClimb` 0x1005bec0). Roll 0.75
  and the super-jump landing 0.75 as in 3.0; rolling out of a super-jump landing sets
  `m_flNextAttack = 0.75 * slowInv` (`PostThink` 0x10054180).
* **Keys:** roll-out and get-up take `IN_JUMP | IN_ALT1` only (`button & 0x4002`).
* **Moves:** no wall dive (`HandleStunt` 0x1005b9f0, `HandleWallClimb`); jump while gliding
  takes the wall-jump branch, not the climb; `HandleStunt` leaves the close-combat window alone;
  `GoWheel` (0x1005d0e0) and `GoRoll` (0x1005d600) don't wait for the jump kick's cooldown.
* **Jump kick cooldown** (`StuntRules::kick_cooldown_on_try`, #125): `CloseAttack`
  (0x1005cd00) arms `kickCD = time + 0.7 * slowInv` and draws the move (`RandomLong(0, 2)`)
  right after its gate, before `CloseCombatAttack`, so a miss also waits out the cooldown: a held
  jump tries one kick per 0.7 s. 3.0 does both only after a hit.
* **Recovery end** (`Play`): clears `ROLLING | GO_DUCK | RECOVER` only and leaves `BlockPlayer`'s
  lock running (3.0 also clears 0x80000 and 0x2 and ends the lock).
* **Wall-landing pose** (`StuntRules::wall_jump_pose_holds_until_recovered`, #112): `Play` ends a
  recovery early once the playing sequence finishes (`recover < time || m_fSequenceFinished`), so
  `Animate`'s priority decides when the wall landing's 0.5 s recovery and its `RECOVER` input lock
  end. 2.1's case 0x36 (its wall-jump id, the port's 0x37; `Animate` 0x1003d8b0) holds the pose
  while `!m_fSequenceFinished && alive && GO_DUCK && !ladder` against everything but the two wall
  poses, on the ground too and against a dive; `GO_DUCK` stays set until the recovery ends. 3.0
  holds it only in the air and lets a dive through, so it switches to the ground poses on landing.
* **The rest of `Animate`'s priority** (#112, `StuntRules`; 2.1's ids from 0x30 up are the port's
  minus one, and its 0x21 is `katana_duck`, the port's 0x25): a playing `goduck` (5) holds while
  unfinished, alive, duck held and not yet `FL_DUCKING`, against everything but a roll, dive, jump,
  the super jump, the duck kick and `katana_duck` (`goduck_holds`; 3.0 has no case 5); the prone
  side roll holds while a strafe key is held (`button & 0x600`, `side_roll_holds_on_strafe_keys`;
  3.0 tests the velocity against the view's right); the wall-climb pose has no dive exception
  (`wall_climb_pose_lets_dive_through`); a playing melee move refuses every non-stunt id until it
  ends, with no `GaitCloseCombat`, `cc_flag` or on-ground condition (`melee_gait_follows`); the
  legs' idle reads only the torso extension, not `m_szAnimExtention` (`gait_idle_anim_extension`).
* **`Animate`'s torso choices** (#174, `StuntRules`): the standing shot plays its `2` pose
  (`shoot_onehanded2`) for a one-handed extension (`strncmp(ext, "one", 3)`) while the stored
  horizontal speed is below 180 and not `FL_DUCKING`, and the shot timer runs as for any shot
  (`fire_pose_2: SlowOneHanded`, 0x1003e8c9..0x1003e96f). 3.0 plays it within a 3 s hold timer
  after a get-up, dive end, roll, wheel, wall pose or melee move, unzoomed, for one- and
  two-handed extensions, and zeroes the shot timer; 2.1's `CTSAnimation` has no hold timer, so the
  port doesn't arm it. The idle refresh (ids 1/6) never plays `m_szAnimExtention`
  (`idle_anim_extension`) and picks the aim poses from the shot timer alone, not while zoomed
  (`aim_pose_while_zoomed`). A melee move's legs follow from 80 u/s, not 120
  (`melee_gait_speed`; FUN_1003f680, 2.1's `GaitCloseCombat`, `fcomp [80.0]` at 0x1003f711), which
  picks `HandleCloseCombat`'s flags and the leg tail.
* **Animation timers and rate** (#112): `CTSAnimation`'s "recently shot" (`time + 2·slowInv`),
  grenade (`time + slowInv`) and bullet-dance (`time + 0.15·slowInv`, `time + 3·slowInv`) timers are
  end times from the stunt clock (`StuntRules::anim_end_times`; `Animate`, `HandleCloseCombat`
  0x1003f340, FUN_1003ee00/FUN_1003ee50), tested as the x87 does: the aim poses `!(shot < time)`
  and the legs' `combat_idle` `!(shot <= time)` (a NaN counts as running for both, #174), the
  whole-body follow `shot <= time` (a NaN is neither). `PreThink`'s `framerate` is
  `1 / FixedSlowMul(fuser1)` from a tenth of normal speed up and 0 below it
  (`ServerRules::anim_framerate`). The side roll's direction is `v_forward` normalised
  (`HandleSlide` 0x1005c1f0, `StuntRules::side_roll_normalizes_forward`).
* **Direction rounding** (#222, `StuntRules`): `Animate` (0x1003d8b0) normalises the velocity
  for the in-air jump blend, the jump pose, the dive start and the death pose with the
  out-of-line `Vector::Normalize()` (FUN_10011fc0), which stores `1 / len` as a `float` before
  the products and tests the zero length IEEE (`anim_normalize_stores_reciprocal`; 3.0's keeps
  the reciprocal unrounded). `CheckForBreakables` (0x1005c680) sums the dive direction
  `x² + y² + z²` (3.0: `z² + x² + y²`), tests its zero length IEEE, and lets a NaN speed past the
  64 u/s gate (`breakables_ieee_xyz`). Both apply under `mp.dll`'s arithmetic (`ts_pm_arith
  msvc`, the default); `gcc` keeps `ts_i386.so`'s.
* **`GoSlow`'s release** (0x10055220, `ServerRules::on_go_slow`, #112): back to normal speed,
  `m_flNextAttack = min(m_flNextAttack, 1)` (a NaN stays) and, with the TS gun active, its two
  next-attack times take that value. It runs for the activator and for every player the power-up
  slowed when it ends (`DeactivateSlowMotionFlow` FUN_10057610, issue #223).
* **Grenade fuse** (`CM61Grenade::WaitThink` 0x100477e0, `ServerRules::grenade_fuse_step`, #112):
  `FixedSlowAmt(fuser1) * 0.1 + elapsed` with the 0.1 floor and the `double` 0.1 (3.0: at least
  0.01, `0.1f`). The other projectiles (knives, world guns) read `fuser1` as it is in 2.1 (0 meaning
  normal, no floor), and the thrower hands over its own `fuser1`; the port keeps 3.0's 0.01 floor
  there, which differs only below a hundredth of normal speed.
* **Wall chain:** `time + min(10, slowInv * max(0.5, chain))` (`GoWallJump` 0x1005b320,
  `GoWallClimb` 0x1005b550). `GoWallJump` tests the cap with the unrounded `double` sum it has
  just stored as the chain (`fst dword`, then `fstp qword` 0x1005b442, compared at 0x1005b466);
  below the cap it computes the cooldown from the stored `float` chain again (0x1005b473..
  0x1005b494, issue #226). `GoWallClimb` reloads the stored `float` throughout.
* **Bullet time** (`GoBulletTime` 0x1005b160): only while slowed (`fuser1 != 0` in 2.1, any time
  scale but 1 in the port), no ×0.7 dodge window, and `m_flNextAttack = 0.55 * slowInv` if it has
  run out.

## Protocol (issue #100 §1.2, checklist item 14)

`ts21-server`'s `protocol` module. The wire stays TS 3.0's: the same message table, sizes and
encodings, so both TS 3.0's client and the port's play 2.1 mode.

* **Outgoing messages** (`ServerRules::outgoing_message`, which every message the server sends
  passes): a message written in 2.1's shape leaves in 3.0's. `ScreenFade` (2.1's
  `UTIL_ScreenFade`, FUN_10067180) goes out as `TSFade` with the same 10-byte body; a 13-byte
  `TSFrags` type 0 (2.1's breakable glass) gets 3.0's hit, damage-bits and damage tail: no hit,
  `DMG_BULLET` and no force, so TS 3.0's client takes its bullet branch with no push and scatters
  the shards `(±9, ±9, 0..10)` as 2.1's client does (zero bits would throw them all toward +x, +y,
  +z; issue #232); a
  2-byte `WStatus` gets the count 1 that 2.1's client showed.
* **2.1-only messages** aren't registered, so they can't be sent. `DelObj(idx)` is
  `protocol::del_obj`: `ShowObj(idx, 0)` to everyone. `Flashlight`/`FlashBat` are never sent
  (TS's flashlight is a weapon attachment, `ActItems`); 2.1 registered `GloSlow` and `KAlign`
  but never sent them. `Objective` needs no `ShowObj(idx, 1)` after it: TS 3.0's client makes the
  slot visible itself (0x1004bc50; the decomp's protocol report says otherwise).
* **Player state** keeps 3.0's encodings, which the shared movement reads on both sides:
  `fuser1` 1.0 at normal speed (2.1's 0 would freeze 3.0's movement) and 3.0's `iuser4` stunt
  bits (2.1's glide 0x80000 and super-jump start 0x100000 are 3.0's 0x100000 and 0x200000). Code
  ported from 2.1 converts with `protocol::time_scale` and `protocol::stunt_bits` (and
  `stunt_bits_21` to read).
* `KFuPower` needs nothing (2.1's byte and 3.0's char are the same byte for 0..100), and
  `delta.lst` stays 3.0's.

## Damage (checklist items 4 and 5)

`crates/ts21/server/src/{damage,explode,blades}.rs`, through the damage hooks of
[gameplay-plugins.md](gameplay-plugins.md) §5. Every value was checked in the 2.1 decomp and,
where the decomp hides it (x87 code, call arguments), in the disassembly of `mp.dll`.

**Bullets** (`ShootBulletsPlayer` 0x1003fd40, the bullet manager's update `FUN_1003f910`):

* Each pellet that hits adds `RANDOM_FLOAT(0, 0.05)` to a multiplier that starts at 1.0 once
  per `ShootBulletsPlayer` call, so it **accumulates over the pellets of a shot**: a shotgun's
  `k`-th hitting pellet gets `1 + Σ U(0, 0.05)` over the hits so far. With `damagemult` in force
  (`sv_cheats`) the multiplier restarts from it on every hit. A penetration carries `left × m` on.
  A simulated bullet starts its own multiplier at 1.0 on every update.
* The range-falloff index is truncated (MSVC `__ftol`), for the hit and for the penetration's
  30-unit index; 3.0 rounds.
* Penetration looks `min(left, 48)` past the hit (3.0: `min(2·left, 48)`).
* The traces are the plain `UTIL_TraceLine` (`FUN_10067850`), not 3.0's
  `UTIL_TraceLine_Expanded`: a player's hitboxes outside its box can't be hit.
* `realbullet` does nothing: the weapons read a global nothing writes (`DAT_100aca80`). Only the
  shooter's slow motion fires simulated bullets, stepped every 0.1 s, at the shooter's time scale
  (×0.2 with bullet time; 3.0 has a `1 − s²` curve).
* Bullet damage runs in 2.1's order (`bullet_damage`): `(int)ammo.damage × falloff × mult` for a
  hitscan pellet, `ammo.damage × mult × falloff` for a simulated bullet, from the 2.1 tables'
  `ammo_damage` and `damage_multiplier`; the multiplier is the one the gun used (the silencer's
  `× 0.8` included), recovered from `Shot::damage`.

**The victim** (`TraceAttack` 0x10053310, `TakeDamage` 0x10052cf0, `Killed` 0x10052390):

* Stunting ×0.7 only; no dodge window. A head hit with `DMG_BULLET` doubles, shotgun pellets
  included; thrown blades are never headshots. Legs ×0.5. 2.1 has no `glast_headshot` and no
  headshot kill message, so its hits don't record one.
* Armour covers hitgroups 2..5 against everything but `0x40e0` (so slashing shrapnel is
  covered). A hit no bigger than the armour uses up that much armour and halves; a bigger one
  empties it and deals `dmg − (dmg − armour)`, exactly the armour that was left. That shipped,
  so the plugin does it too. The damage is truncated to an int, as in 3.0.
* Every hit kicks the victim's view up 3° (`punchangle.x -= 3`).
* `Killed` sends no `TSMBlur` (and makes no rolls for it).

**Explosions** (`CM61Grenade::WaitThink` 0x100477e0, `TSExplosion` 0x10047aa0):

* The grenade deals 100, full damage to 128 units, nothing past 1024.
* No dropped gun is pushed.
* Every explosion (grenades and exploding breakables) sprays `RANDOM_LONG(30, 45)` pieces of
  shrapnel from the blast point at 2000 u/s plus the attacker's velocity, each 100 damage
  (`DMG_NEVERGIB | DMG_SLASH`) to the player it touches. The piece is 3.0's `shrapnel` entity
  (`CTSShrapnel`, which 3.0 never creates), made by `entities::ts::shrapnel::create` (a port of
  3.0's dead `CTSShrapnel::Create`); 2.1's `Spawn` leaves it visible (no `EF_NODRAW`) with
  `iuser4 = 1`.
* Then the spectacular slow-motion point is `(0.15, 1.5 s)`.
* The per-target arithmetic is 2.1's (`ts21_server::explode::explosion_hit`, #220): the distance
  from the unrounded differences (`(z² + y²) + x²`; mp.dll 3.0 stores them), the direction's
  `Normalize` with `1/len` stored as a `float` (`blast_dir`), a NaN distance deals 0 (3.0: the
  full damage) and a NaN occluder thickness stops the hit (3.0: hits).
* `g_vecAttackDir` (`CBaseMonster::TakeDamage` 0x10011630, which `Killed` pushes the body against
  and the death pose reads): the first normalisation keeps the x difference unrounded and
  multiplies z by its stored copy, `(z·z_f + y_f²) + x²`; a NaN length isn't zero
  (`ts21_server::damage::attack_dir`).

**Screen shakes and fades** (`UTIL_ScreenShake` 0x10066f50, `UTIL_ScreenFade` /

the level-change fade, `TakeDamage`'s red flash and `TSInit`'s spawn fade.

**Melee** (`crates/ts21/src/shared/melee.rs`, `MeleeRules` on `Ts21`, which both sides run;
`crates/ts21/server/src/melee.rs` for the victim). Entered only on a fresh press, as 2.1's
`PrimaryAttack`/`SecondaryAttack` do. Delays are fixed when set (`× 0.5` with Double Fire Rate

## Deviations

* **3.0 view models and sprites (visual compatibility).** 2.1 mode plays with TS 3.0's content,
  which 2.1's client and server code doesn't drive the way 3.0's does. Only the look changes; no
  rule, damage or gameplay timer does:
  * **Reload.** 2.1 played the reload view animation from `ReloadWeapon`'s `SendWeaponAnim`
    (mp.dll 0x1004ce20; the shotgun phases in 0x1004cea0, slots `[1]`, `[8]`, `[9]`, `[10]` as
    3.0's), and its reload event (client 0x10078940) none. The port's shared reload sends no
    weapon animation (3.0 plays it from the event), so 2.1 mode showed none: the reload event
    plays 3.0's view animation by the phase in every mode, and `reload_sound_phases` keeps 2.1's
    sounds. 2.1's sawed-off with rounds left played `[8]`; 3.0's `[1]` is played.
  * **Lasers.** 2.1's `laserbeam.spr` (64×64) and `laserdot.spr` are red in the texture (red
    channel only), so its code draws the beam in a grey flicker and other players' dots white.
    TS 3.0's (32×128 and 64×64) are grey and coloured by the code, which made 2.1 mode's lasers
    white. `LaserStyle::sprite_tint` (red) puts 2.1's colour back.
  * **Kung fu.** 2.1 has no kung-fu view model (`HolsterWeapon` leaves `viewmodel` 0), so the
    `CloseCombat` event's 3.0 view animations (already sent in 3.0's form) and the kung-fu idle
    had nothing to play on. `holster_draws_kungfu` is true, as 3.0's: `v_melee.mdl`, its draw
    animation and the draw event. 2.1's kung-fu idle (`FUN_1004dc40`) plays nothing and only
    re-arms its timer, which `CCombatAttack` sets to the move's delay; the port's plays 3.0's
    idle animation, which then cut a 3.0 move short (a jab after 0.15 s), so a move that played
    sets the idle timer to 3.0's 2 s. A 2.1 block (`CCombatBlock`) sends the owner 3.0's block
    view animation (set A `[1]`, as 3.0's event plays at 0x100433bb) through `SendWeaponAnim`,
    not skipping the local client, which doesn't predict the block, and sets the idle timer to
    3.0's 3 s. No `CloseCombat` event is sent: 2.1's (client 0x100792e0) has no block branch and
    would play closecombat.wav and trace on an original 2.1 client. So in-eye spectators don't see
    the block, and the third-person block animation (3.0's `player_anim(0x26)`) isn't played,
    since the player's sequence also places its hitboxes (issue #324).
  * **Slow-motion tint.** 2.1 has no `cl_slowfade` and writes no screen fade for slow motion (its
    only cue is the `slowmotion.spr` icon). 2.1 mode also draws 3.0's (0, 100, 125) tint at
    `(1 − ts) × 50` while slowed (`slowmo_tint` true); the icon stays and `cl_slowfade 0` turns the
    tint off (issue #324).

* **The server browser's Game column** (port addition): `GetGameDescription` says
  "The Specialists v3.0.2 (DM-21)", likewise `LMS-21`, `Teamplay-21` and `The One-21` (and `(21)`
  without rules), so 2.1 servers are told apart from 3.0's ("The Specialists v3.0.2 (DM)").

* **TS 3.0's client is refused** (port addition, issue #100 §1.1): `ClientConnect` refuses a
  client without the port's `_tsrs` userinfo key with `Invalid Version: Running 2.1 mode.
  Upgrade to the rust port at tsmod.org` (`ts21_server::REFUSED_CLIENT`; bots and HLTV always
  join). TS 2.1's own clients could never join this server (its protocol is 3.0's), and TS 3.0's
  client can't predict 2.1.

* **Weapon events (issue #160).** The gun smoke's cooldown keeps 3.0's eased slow time (2.1: the raw factor's).
* **Client bullets (issue #165).** 2.1's trail particles run through 2.1's particle update (`ParticleModel::Decelerate`, issue #261). A bullet model's detail body is chosen when the draw queues it (this frame's cull origin), not one frame later in `HUD_CreateEntities`, and 2.1's adaptive low-detail flag (0x1031b819, which forces body 0) isn't modelled. The hit's damage left is `(base × mult) × falloff` with the product already rounded to a float (the weapon table's `damage`); 2.1 multiplies the ammo's integer damage, the event's multiplier and the falloff on the x87 stack.
* **`TSFrags` and blood particles (issue #232).** 2.1's glass, explosion and blood builders write their values into 2.1's particle slots, which run through 2.1's particle update (`ParticleModel::Decelerate`, issue #261), so the gravity, fade and scale-speed values are in 2.1's units. Fields 3.0 has and 2.1 doesn't (react, drag, stretch) stay zero.
* **Unused 2.1 particle code.** 2.1's particles have a follow field (`+0xba`/`+0xbb`: an entity's attachment plus an offset, `0x100902f0`) and a per-frame think callback (`+0xd0`); the port's have neither. Only unreferenced builders set them: the attachment-following muzzle flash `0x1007fe50` (the fire events use `0x10080a30`) and the concrete-impact builder `0x10083b30` with its smouldering chip (think `0x10083740`) and landing puff (collision `0x10083590`) (the impacts use `0x10084240`). No call, jump or pointer reaches either (issue #267).

* **Client prediction uses 2.1 `mp.dll`'s arithmetic, not 2.1 `client.dll`'s.** 2.1's client
  was built without optimisation and rounded more often. The difference is in the last bit only,
  and it made 2.1's prediction disagree slightly with its own server. Following the server keeps
  both sides identical, as the port does for 3.0.

* **Kevlar's loadout bit.** 2.1 marks a bought vest in its own item mask (`+0x690`). The port's
  loadout bit is 3.0's slot-carrying vest, so a 2.1 vest leaves it clear (it weighs nothing).
* **A NULL attacker** in `PlayerKilled` is the world (TS would dereference it).

* A refused classname is matched without case: whether an engine finds a differently cased
  export depends on the engine, and 2.1 has none of these classes in any case.
* `ts_mapglobals`'s weapon mask is applied when the first one spawns, not on the rules' first
  Think. The two differ only if that entity is removed before the first frame.
* A broken breakable or door has no think. 2.1's (FUN_10015e10, the vtable slot 2 default) only
  pushes `nextthink` on by a second, which does nothing.
* `RespawnEntities` runs the plugin API's `BreakableRespawn` hooks (`ham`), as 3.0's does.

* **Floating point.** The crosshair gap and the kung-fu regeneration run on the x87 stack in
  2.1. The port uses f64, which can differ only when a result falls within about 2⁻⁵³ of a
  truncation boundary. The single-precision stores (`NextStunt`, `TSSlowMo / 100`, `now − last`)
  are exact in f32.
* **`default_fov` after a 2.1 map** (port addition). On a 3.0 map after a 2.1 one, the cvar's
  value is read back from its string, so the 2.1 pin to 80 doesn't carry over into 3.0.

* ~~The client's kick target and a bot's `punchangle` add the kick's yaw as a rounded `float`.~~
  Fixed (#278): `GunHost::kick` takes the yaw as `f64`, and 2.1 hands over the unrounded
  product (client `0x1001ea26`, server `0x10049c7c`).
* ~~The client's view-angle kick target uses TS 3.0's smoothing.~~ Compared (#278): 2.1's
  `V_ApplyKick` (`0x10097de0`) is 3.0's ease, settle test and zeroing, but stores the
  differences, the squared length and both steps to floats, and a NaN length keeps easing;
  `ClientRules::dll_build` (`Debug`) selects that form. 2.1's gun punch
  (`V_CalcGunAngle` 0x100b6610, `∓1.25 × ev_punchangle`) is always 0, as the port has it: the
  two functions that would write `ev_punchangle` (0x10096310, 0x100964a0) are dead (their
  thunks 0x10003e40 and 0x10002239 are never called or referenced), and its `KAlign` handler
  (0x10088480) never runs because 2.1's server registers `KAlign` but never sends it.

* **Time scale encoding.** The port keeps 3.0's `fuser1 = 1` for normal time (issue #100 §1.2).
  2.1's `FixedSlowMul` maps its normal 0 to 1; the port's stunt clock maps 1 to 1, and a 0 (which
  2.1 mode never sets) to 10.
* **Bits and animations.** 3.0's `iuser4` layout and animation ids stay (the 3.0 player models).
* **x87 maths in `f64`.** The timer arithmetic (`double` durations, 80-bit products, stored as
  `float`) is done in `f64`; the `float` results can differ in the last bit in rare cases.

* **`PTakeDam`'s amount byte keeps 3.0's encoding** (half the damage, ×8 for shotgun pellets,
  +128 for a kevlar hit), computed from the 2.1 damage. 2.1 sends `min(dmg, 255)`, or 0 for a
  kevlar hit, which a 3.0 client would draw as the wrong blood (issue #100 §1.2: 3.0's wire format
  carrying 2.1 values). The port's client in 2.1 mode decodes it back for 2.1's blood: kevlar is
  0, else twice the low 7 bits (at least 1); a pellet's ×8 can't be told apart, so a buckshot
  hit bleeds more drops than 2.1's.
* **Shrapnel without an owner** (an explosion with neither attacker nor inflictor) keeps its
  spawn state; TS would read a null pointer.
* **Melee animations** use the port's (3.0's) animation ids for the matching move: 2.1's table
  numbers the blade swings differently. The kung-fu move ids are the same in both. The `CloseCombat`
  event carries 3.0's view-animation index for the move.
* **A kung-fu block's damage to the blocker** uses the generic hitgroup and the blocker's origin
  (2.1 passes the attack's trace), and the block's own `PTakeDam` keeps 3.0's encoding. The
  blocker's block animation (0x22) isn't played.

* **Bots' texts are embedded.** 2.1 reads `<gamedir>/bots.txt` and `bot_say.txt`; in 2.1 mode the
  port uses 2.1's shipped files compiled into the plugin (the game directory holds 3.0's), so a
  server can't edit them for 2.1 mode.
* **The weapon slot menu past its grid.** 2.1's `SelectSlot` can leave the row at 17 or start a
  fast-switch search at 18, reading the fields after the grid as weapon ids, and spins forever
  when such a search finds nothing; the port reads those rows as empty and stops after one round.
* **Objective texts** are cut at 63 characters, as 3.0 does; 2.1 copies up to 64 bytes into a
  44-byte buffer (`CTSObjectivePointer::Use`), which a longer text overflows.
* **The observer's target handle.** 2.1 keeps a raw `CBasePlayer *`; the port keeps 3.0's slot
  index and tests that the slot still has its player, as 3.0's camera does.
* **Bot guards.** An enemy or listed player whose edict lost its player is skipped (TS keeps a raw
  `CBaseEntity *`). `LookAround` with a `keepGoal` other than 0 or 1 (2.1 would use uninitialised
  angles) leaves the view alone; the port only ever stores 0 or 1. The bots' `fcos`/`fsin` are
  Rust's `cos`/`sin` on `f64`, as for 3.0.
